# T1c: spec 010 A1 probe (otto/mamoru#315), 2 Nov 2026

Forks: Base 53,140,000, Monad 116,980,000, Ethereum 26,328,000 (public archive RPCs). Code: branch
`feat/316-v4-no-guardian` (V4 without guardian or registry, MamoruGasPolicyV2 with the clock-free rate, MamoruV4Table).

## 1. The gas policy's time range is intersected by SmartSession and enforced by the EntryPoint

`V4UserOpFork.test_claimedTimeOutsideSlackRefused`, through the deployed SmartSession v1.0.0 (code hash pinned in
`base.json`) and EntryPoint v0.7 on Base:

- a batch whose `clock(T)` is 301 s in the past, or 301 s in the future, is refused at validation with `AA22 expired or
  not due`;
- 299 s in the past validates and executes.

So SmartSession passes a userOp policy's `validAfter` / `validUntil` through (`PolicyLib` intersects every policy's
validation data) and the EntryPoint enforces it: MamoruGasPolicyV2 knows the time within S = 5 min without reading
`TIMESTAMP`. **Answered: yes.**

## 2. A V4 session op's validation follows ERC-7562 (the bundler question)

`V4Erc7562Fork` records every opcode of the account's `validateUserOp` as the EntryPoint calls it (Safe -> Safe7579 ->
SmartSession -> MamoruGasPolicyV2 and MamoruActionPolicyV4 -> MamoruV4Table) and applies the rules a bundler applies to
an unstaked account: OP-011 (no TIMESTAMP, NUMBER, BLOCKHASH, COINBASE, PREVRANDAO, GASLIMIT, GASPRICE, BASEFEE,
BLOBHASH, BLOBBASEFEE, ORIGIN, BALANCE, SELFBALANCE, SELFDESTRUCT, CREATE, CREATE2), OP-012 (GAS only before a call),
OP-061 (no CALL with value), STO-010/021 (every SLOAD/SSTORE in the account's own storage or associated with it:
keccak(account ‖ x) + n, n < 128, preimages tracked from the trace). A control test proves the checker catches a
TIMESTAMP and a foreign SLOAD.

| Batch | Violations |
|---|---|
| swap (clock, approve, V4.swap, reset, assertZero) | 0 |
| exit (clock, checkExit, decreaseLiquidity, collect) | 0 |
| bridge (clock, approve, V4.bridge, reset, assertZero) | 0 |
| readiness relay (clock, MessageTransmitterV2.receiveMessage) | 0 |

**Answered for every rule above: yes, in every frame**, the deployed Safe, Safe7579 and SmartSession included.

Not run, and why: a live bundler (Alto, Rundler, Skandha) needs a geth-style JS or native tracer that anvil does not
serve, so OP-041 (EXTCODE* on a codeless address), OP-054 and the reputation system were not exercised by a bundler.
None of V4's or the gas policy's validation paths touches a codeless address or the EntryPoint. The remaining check is
one op through a public bundler (Pimlico accepts EntryPoint v0.7 on Base, Ethereum and Monad, read 2 Nov) after T7, on
an account with dust.

## 3. CCTP V2 messages between V4 instances

The receiving transmitter's attesters are replaced on the fork by one test key (the attester manager's own calls,
pranked): a stand-in for Circle's attestation, never a weaker check on V4's side.

- **Monad -> Base** (`V4RemoteFork.test_I4_remoteEndToEnd`): `announceReady` on Monad (read back + `sendMessage`, 67k
  execution gas) emits a V2 message from V4 to V4, finality 2000, open destination caller; on Base the account's own
  session relays it with `receiveMessage` (a userOp, the user pays), MessageTransmitterV2 calls
  `handleReceiveFinalizedMessage`, V4 writes readiness, and the next userOp burns to the remote.
- **Base -> Ethereum** (`V4EthereumSiblingFork`): a home Safe on Base announces to its sibling on Ethereum; delivered with
  `receiveMessage`; the sibling bridges home.
- The message layout V4 sends was read back field by field (`test_A1_announceReadyRefusals`); the handler's refusals
  (sender, source domain, finality, unfinalized, stale owners, look-alike Safe) are in `test_A1_readinessMessageChecks`.

**Answered: yes on Base <-> Monad and Base <-> Ethereum**, with the canonical transmitter at the pinned code hash on all
three chains.
