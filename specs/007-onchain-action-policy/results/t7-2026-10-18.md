Why P1 4 mattered: EntryPoint v0.7 charges `min(maxFeePerGas, basefee + priority)` (or `maxFeePerGas` outright when the
two are equal) and takes a prefund of `maxFeePerGas x gas limits` from the Safe. With only the priority fee capped, the
price was bounded by basefee + cap and the prefund not at all: one op could move the Safe's whole ETH into its
EntryPoint deposit.

`V4_GAS_CAPS`: priority 0.01 gwei, maxFeePerGas 0.1 gwei (about 20x Base's usual 0.005 gwei basefee; the engine's
`2 x basefee + priority` fits up to ~0.0495 gwei and is clamped above it), verification 3M, call 2M,
preVerification 200k. One op costs the Safe at most 0.1 gwei x 5.2M = 5.2e14 wei.

## Max loss with a leaked key, gas included

```
L <= sum_p (band_p + fee_p) x (V_p + 2 x min(T_p, W_p x (1 + tau / 1 day)))      (tokens, unchanged)
   + min(E, U x c_op)                                                              (gas)
c_op = maxFeePerGas_cap x (maxVerificationGasLimit + maxCallGasLimit + maxPreVerificationGas) = 5.2e14 wei
U    = sum of the usage limits of the v4 sessions = 3 pools x (3,000 + 1,000 + 32,000) = 108,000 ops
E    = native ETH the Safe holds plus its EntryPoint deposit
```

`U x c_op` is 56 ETH, so `E` binds: the relayer tops the Safe up to `gasReserveWei + margin` (5e-4 ETH) at activation
only, about one op at the cap. The gas term per account is therefore the Safe's ETH, bounded per op at 5.2e14 wei,
and never its tokens (WETH is an ERC-20; gas is paid in native ETH only). At 1,000 USDC and ETH at 2,500 USD that is
about 1.3 USDC (0.13% of the cap) on top of the token table in the spec. Before P1 4 the per-op figure was unbounded
in `maxFeePerGas`.

## T7 (c): activation and renewal in consecutive owner transactions

Operator (`apps/mamoru-operator/src/operator.ts`), only when `MAMORU_ONCHAIN_POLICY_V4=1` and both
`MAMORU_ACTION_POLICY_ADDRESS` and `MAMORU_GAS_POLICY_ADDRESS` are set (`boot.ts` `resolveV4Policy`/`deployedV4`):

- `v4Context`: both policies must have a ModuleRecord under the resolver of Mamoru's other policies (`findModule`),
  else `ACTION_POLICY_NOT_REGISTERED` and nothing is attested; each one the Safe has not attested yet
  (`findAttestation`) is attested in the first transaction; generation = `generationOf + 1` for a full approval
  (activation, renewal, the move from v2/v3), the current one for an extension, which is refused
  (`POLICY_GENERATION_MOVED`) unless every pool the account holds is configured at it; `Init.admit` = the account's
  `admittedTokenIds` still owned by the Safe, grouped by the v4 pool they belong to (at most 64 per pool,
  `ADMIT_TOO_LARGE`).
- `fitV4`: keys in `orderV4Keys` order (buckets by preference, enter-swap, enter-mint, manage-any), split by
  `splitV4Keys` with the transaction's own overhead (revokes, trust, attest) off its ceiling; the first part is built
  and simulated (a per-action static estimate when it cannot be, e.g. an undeployed Safe) and must fit the activation
  (15M) or renewal (16.2M) budget, else its last session moves to the next part.
- Each part is one ordinary owner op on the existing machinery: activation = `activate`; the move from v2/v3 and a v4
  renewal = `renew` (revokes everything the account has, every #60/#65 rule as before); every later part = `renew`
  with `extend` (`planExtend`), at the same generation.

Multi-transaction states (the renew row drives each step; nothing new is persisted):

| State | On chain | Operator |
|---|---|---|
| S0 | v2/v3 grants (or none) | `policyId` v2/v3; `approval.upgrade` when the flag is on |
| tx 1 sent | | one renewal in flight (`RENEWAL_IN_FLIGHT`), engine held while an op is unsettled (`ENGINE_BUSY`), reconciliation by receipt or `ExecutionSuccess` only (I2), `settleRenewals` for an unread receipt |
| S1: tx 1 landed | old grants revoked; generation G enabled for the first part; both policies attested; positions of the covered pools admitted | `afterOwner` (also on a late receipt) moves `policyId` to v4 (read from the grants); `acc.grants` = part 1; `missingGrants` = the rest, so `approval.missing` and the row offers the next step; the engine runs with what it has (`SESSION_MISSING` for the rest) |
| tx 2 sent | | as tx 1 (`extend`: must find exactly the grants it was built on, else `RENEWAL_STALE`) |
| S2: tx 2 landed | the rest enabled at G | full set |
| tx 1 fails / never signed | nothing changed | S0 |
| tx 2 never signed | S1 stays | the row keeps offering it; a due or usage renewal is a full one at G+1 (split again), which revokes S1's grants |
| generation moved under S1 (an owner enable elsewhere) | | the extension is refused (`POLICY_GENERATION_MOVED`); a full renewal resets |

Activation of a new account (operator policy `conservador-live-v4`) follows the same path from `planActivate`: part 1
in the activation (trust + attest + enable), the rest through the row.

A STOP after S1 or S2 revokes whatever is enabled, as before. `startLoop` passes each session's `Init.admit` to the
engine's precheck mirror (`StoredGrant.admit`), and the engine reads `admittedPool` once for a position it does not
know yet (after a restart), so the mirror matches the chain.

Not done: a fresh session key per renewal (spec "Fresh key per renewal"). The renewal keeps `acc.sessionKey`; new
permissionIds and ConfigIds come from the new salts, the generation retires every older config, and the same
transaction revokes every old permissionId. Rotating the key needs the engine and the key store to switch keys on a
receipt; left for a follow-up.

## T7 (d): the renew row

`approval.upgrade` (domain `FundingView`) is set while the move is offered. The app shows the existing row with its own
title (`homeCopy.upgradeTitle`) and the Renew button; everything the owner signs is the operator's summary in the
unified approval dialog: one line per pool with the band (and the stables anchor), `W_p` per day and `T_p` in total, a
line with the gas cap per engine transaction and the number of transactions the grants allow, the validity in days,
the cap, the positions admitted, and how many steps the approval takes.

## T7 (e): usage-triggered renewal on the policy's budgets

`refreshChainUsage` also reads, for a v4 account, `generationOf`, `configOf` and `budgetLeft` per pool
(`readPolicyBudgets`); `usageView` counts each pool's spent share of `T_p` (`budgetUsedBps`) like a grant's usage, so
`approval.usage` (action `enter`, that pool) appears at `USAGE_RENEW_BPS` (80%) before `T_p` binds.
